# AGENTS.md

## Purpose

This repository contains Chanchai Charnataparporn's CV. `base.md` is the canonical source for the CV wording, and the published artifact is a static HTML document with a two-page A4 print layout. A dependency-free Node.js AWS Lambda handler serves the same HTML through the owner's existing API Gateway HTTP API. GitHub Actions packages two files into a ZIP and updates the existing Lambda with the AWS CLI. There is no local application server, package manager, application build step, SAM template, or CI test suite.

## Canonical files

- `base.md` is the canonical content source. Every CV wording change belongs here first.
- `chanchai.html` is the canonical presentation source and contains the **Print / Save as PDF** button. Its CV content must match `base.md` exactly after applying the rendering rules below; it is synchronized manually rather than generated by a build step.
- `index.cjs` reads that exact HTML from disk and returns it as a string in a standard Lambda proxy response.
- `.github/workflows/deploy-lambda.yml` assumes an AWS role through GitHub OIDC, packs `index.cjs` and `chanchai.html` into a ZIP, and runs `aws lambda update-function-code --publish`.
- `README.md` documents viewing, printing, updating, deployment configuration, and reviewing the CV.
- `.gitignore` excludes private sources and generated files.

PDFs are on-demand exports only; they are not repository artifacts. Never add `chanchai.pdf` or any other PDF to Git. PDF creation must go through the **Print / Save as PDF** button in the HTML, not through a generated file committed alongside the source.

## Content rules

- Treat `base.md` as the sole source of CV content. Do not rephrase, correct, summarize, or supplement its wording from older HTML or other career sources unless the owner explicitly changes that source.
- Preserve every literal placeholder, including `TODO`, until it is changed in `base.md`; do not silently fill or hide placeholders.
- Preserve spelling, capitalization, punctuation, hyphen and dash characters, numbers, link text, URLs, and credential IDs exactly. HTML escaping is allowed when required to represent the same visible text.
- Render Markdown links as clickable links with the exact source label and destination.
- `left text -> right text` means a two-sided row: render the left and right text in a flex container with `justify-content: space-between`. Do not display the `->` marker or alter either side's wording.
- `<br>` marks a visible line break. For job/company metadata, preserve the owner's current paragraph style: end the current `<p class="job-meta">` at the source `<br>` and put the following metadata line in its own `<p class="job-meta">`, rather than placing a literal `<br>` inside a shared paragraph. If no further metadata line follows, close the paragraph and continue to the next list or role without adding an empty paragraph. Do not display the `<br>` marker literally or change the metadata wording.
- `### text1, text2, text3` means a tag list. Render each comma-separated value as its own `<span class="tag">...</span>` in source order, trimming only the whitespace around each value. Do not display the `###` marker or commas.
- Structural print controls are presentation elements, not CV content. Do not add career summaries, skill groups, job details, projects, or other substantive content that is absent from `base.md`.
- Do not publish raw resumes, timesheets, work logs, addresses, or other private source material without explicit user approval. The origin repository is public at the time this guide was written.
- The existing API Gateway exposes the public CV. Package only the public HTML and handler in `cv-lambda.zip`; never include private source documents or `base.md`.

## HTML and print architecture

- The document is self-contained HTML with embedded CSS and system fonts; avoid adding runtime dependencies or remote assets.
- Each printed page is an explicit `<section class="page" id="page-N">` inside `<main class="cv">`.
- The current layout has two A4 pages: profile/education plus the Experience heading and complete first role on page 1, and the four remaining roles on page 2. Update this guide, `README.md`, and the print-bar text if the page count intentionally changes.
- `.page` has fixed `210mm × 297mm` dimensions with compact header and bottom spacing. `@page` selects A4 portrait with zero margins.
- `.split-line` implements the `->` mapping with a flex row and `justify-content: space-between`; keep both sides legible without changing their text.
- Do not add CV name/page-number footers; the owner removed them. Keep browser headers and footers disabled when exporting.
- The screen-only print bar is hidden in print media.
- Preserve `break-after: page` / `page-break-after: always` behavior. Keep the Experience heading and first role together on page 1, the four other roles on page 2, and avoid breaking individual jobs, education items, or bullet items where practical. Do not add a second Experience heading to page 2.
- Preserve the **Print / Save as PDF** button and its `window.print()` behavior.

## Editing workflow

1. Check `git status`, the current branch, and `origin` before changing files.
2. Read `base.md` and the relevant HTML; identify whether the requested change affects content, presentation, or both.
3. Make wording changes in `base.md` first, then mirror the content into `chanchai.html` using the exact content rules above. Make presentation-only changes in `chanchai.html`; keep unrelated styling unchanged and keep both guides synchronized with workflow changes.
4. Inspect every page in a real browser, including print media. Check for horizontal overflow, content beyond the page, bottom-edge clipping, broken flex rows, and accidental blank pages. Confirm the Experience heading and complete first role fit together on page 1 and the other roles remain on page 2.
5. Do not add CI tests for this deployment. For handler changes, check JavaScript syntax with `node --check index.cjs` if needed. For workflow changes, lint the GitHub Actions YAML when a linter is available.
6. Review the final diff and stage only the intended files with explicit `git add` commands.
7. Stop for the repository owner's review. Do not commit, push, or trigger a deployment.

The repository owner can open `chanchai.html` and click **Print / Save as PDF**. Use these browser settings:

- 100% scale
- Zero margins
- Background graphics enabled
- Browser headers and footers disabled

Generated PDFs must remain outside Git. Do not create a repository PDF through DevTools, a script, or another build process. If the owner explicitly asks for a PDF verification copy, use the HTML print-button workflow and save it outside the repository; never stage it.

## AWS Lambda and continuous deployment

- Keep the Lambda dependency-free and read `chanchai.html` from disk as UTF-8 with `fs/promises.readFile`; do not add a second canonical HTML copy.
- Export a regular async `handler` that returns a standard Lambda proxy response for the existing API Gateway HTTP API. Do not use `awslambda.streamifyResponse` or `awslambda.HttpResponseStream`.
- Return `statusCode: 200`, the HTML string in `body`, and only the header `Content-Type: text/html; charset=utf-8`. Do not add method handling or extra headers; the gateway owns HTTP behavior.
- The workflow packs exactly `index.cjs` and `chanchai.html` at the root of `cv-lambda.zip` with `zip -j -X`, then calls `aws lambda update-function-code --zip-file fileb://cv-lambda.zip --publish` and `aws lambda wait function-updated`.
- The Node.js 24 Lambda and API Gateway already exist and are not provisioned by this repository. Do not add SAM, CloudFormation, Function URLs, artifact buckets, or gateway resources to this deployment.
- The gateway's HTTP API Lambda proxy integration uses standard buffered responses and does not use REST API response transfer mode `STREAM`.
- GitHub OIDC supplies short-lived credentials. Never add long-lived AWS access keys to workflow files or documentation.
- Use exactly three repository secrets: `AWS_REGION`, `FUNCTION_ARN`, and `AWS_DEPLOY_ROLE_ARN`. `FUNCTION_ARN` is the full ARN of the existing Lambda. Do not reintroduce GitHub variables or other deployment configuration.
- Reference secrets directly where needed; do not map them into `env` variables or echo them in workflow steps.
- The deployment role needs `lambda:UpdateFunctionCode`, `lambda:PublishVersion`, and `lambda:GetFunctionConfiguration` for the waiter.
- Do not add CI tests, a test job, SAM validation/build, or a gateway smoke test to this workflow. The owner deliberately wants a minimal package-and-upload pipeline.
- Pushing the workflow to `main` enables automatic deployment for subsequent changes. The repository owner performs that push and any manual workflow dispatch.

## Verification requirements

A content or layout change requires a real-browser print-layout check before staging.

- Confirm the expected page count; currently two pages.
- Confirm the print layout uses A4 portrait and the intended page breaks.
- Inspect all pages for clipping, overlap, blank pages, broken flex rows, bottom-edge overflow, and unreadably dense content.
- Confirm the Experience heading and complete first role, including all bullets and tags, fit together on page 1, and the four other roles remain on page 2 without a duplicated heading.
- Confirm section endings are present, no content is truncated, and no CV name/page-number footers were reintroduced.
- Compare the rendered CV text and links against `base.md`, including every `->` row, `<br>` metadata paragraph boundary, tag, date, URL, and literal `TODO`; ensure no legacy CV content remains.
- Check that no PDF, private Office document, AWS credential, ZIP archive, test file, or SAM/build directory is staged.
- Do not add or run a CI test suite for this deployment.
- Lint the GitHub Actions YAML when a linter is available and verify the ZIP contains only `chanchai.html` and `index.cjs`.
- Run `git diff --check` and review `git diff --stat` plus the actual diff.
- After staging, review `git status --short`, `git diff --cached --stat`, and `git diff --cached`.

If content overflows, rebalance sections or add a deliberate page rather than clipping content or shrinking the entire document excessively.
